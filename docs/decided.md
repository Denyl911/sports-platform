# Decided

Questions answered, gaps kept as the rule, and features refused with their reason. One entry, a sentence or two; if deciding it took a design argument with an alternative worth naming, it gets an [ADR](./adr/) instead and this file links to it. A question answered here does not get re-argued without new evidence in `docs/adr/`.

Anything still open belongs in [`todo.md`](./todo.md) with its `Needs:` line; a refusal that might be reversed one day also names what would change it.

---

**Why is there no ESLint or Prettier?** Biome is the single tool for lint, format and organize-imports (`biome.json`, `turbo`'s `check` task). Two tools doing overlapping work disagree with each other and with the formatter; one tool, one config, one command. Reconsider only if a rule Biome cannot express becomes load-bearing.

**Why do tests run against a real Postgres instead of mocking the database?** The tests go through the real app (`treaty(app)`), so they exercise routes, guards, services and SQL in one pass; mocking `@sports/db` would test the mock. A throwaway database (`sports_platform_test`, pinned by `apps/api/test/setup.ts`) is cheap, and it is what makes "a column change is one commit" checkable. A `DomainError`-unit test that wants no database may exist, but a route test is not that test.

**Why is there no `apps/mobile` yet, if `biome.json` already ignores its paths?** The mobile app (Tauri) is planned, not built. The ignore rules are written ahead so a landing directory does not start as a lint failure. Anything else that treats the app as existing (docs, CI, contracts) waits for the directory.

**Why does the API accept `tournamentId` in create bodies if the guard resolves it anyway?** The explicit field (ADR 002's pattern in `@sports/schemas`) makes the create contract carry what the write commits to, and lets integrity checks compare the payload against the resolved chain. It is a declaration, not an authorization: a client that lies gets the guard's answer.

**Why is the standing of a group recalculated on every score write instead of a nightly job?** The standings are the product's most-read page and must not lag the score a viewer just saw; a full recalculation per write is bounded by the group's size. The `docs/todo.md` P2 query-budget test is where a cheaper shape earns its place if the cost grows.

**Why is the checks program in `scripts/` called by root scripts instead of being a turbo task?** The scans read the whole repository, not a workspace's build output; a turbo task needs the declaring script inside each workspace's `package.json`, which would either run the scan once per workspace or invent a fake package to host it. One program, one subcommand per rule, root `package.json` scripts pointing at it ([`docs/adr/007`](./adr/007-the-gate-is-one-program-of-scans.md)).

**Why does `packages/api-client`'s test suite preload `apps/api/test/setup.ts`?** The live suite is a genuine E2E: it drives the real `api/src/app` against the real test database, so it needs the same environment the API's own tests pin (NODE_ENV, JWT secrets, `sports_platform_test`). Declaring the environment twice is how the two copies drift; one preload, borrowed by `bunfig.toml`, keeps one source of truth — and Turbo's `^test` ordering keeps the two suites, which share the one database, from truncating it under each other's feet.

**Why is the query ledger opt-in (`DRIZZLE_COUNT=1`) instead of always on?** A ledger that fills during production traffic is a memory leak with a schedule, and the budget only needs the number inside the test's window. The logger hook is Drizzle's own mechanism; with the flag off, every query pays one env check and nothing is stored ([`docs/adr/008`](./adr/008-read-endpoints-pin-their-round-trip-budget.md)).
**Why does `packages/ui` carry `motion` even though the effects could hand-render with CSS?** The bits (react-bits vendored) need staggered reveals, in-view mounting and spring-ish timers in DOM: recreating each one with raw CSS repeats the miniature physics in every bit and drifts. A PR's guidance for what enters `src/components/bits/`: vendored, with tokens, and without a second runtime — [ADR 009](./adr/009-react-bits-comes-in-vendored-on-one-runtime-in-tokens.md). react-bits is MIT + Commons Clause: usable in the product, not resealable as a component product.

**Why do the admin list filters carry `limit`/`offset` without a default, so without limit the list answers every row?** The window the pager needs is a client right (`page=2` in the URL must decide the slice), but the 20-per-page default of `paginationQuerySchema` would have coerced the public lists — clients that never pass `limit` and expect all rows — into silently truncated answers. Absent means all; the only pager in the product (the admin one) always passes its window and reads the `total` of the universe. The server's job is the stable tail (`asc(id)` as tiebreak) so two pages never share a row.

**Why do the admin list pages read their search params with a cast (`Route.useSearch() as AdminListSearch`) instead of typed `validateSearch`?** The typed path has a tax that TypeScript collects from everywhere: once a route declares `validateSearch`, TanStack makes every `<Link to>` and `navigate` targeting that route pass `search`, and a dozen unrelated back-links across the app turn red. The repo already used the cast on pages whose search arrives via parent `Link search={{ ... }}` (ADR's files-and-params idiom); the normalizer (`adminListSearch`) still sanitizes (page > 1, q no vacío) at the single place that reads them. Also learned on the same patch: `navigate({ search: fn })` without `to` does not typecheck — the replacement `navigate({ to: RouteBody, search: { ...search, ...patch } })` does.

**Why is the first tournament taught in place, with a guide and a chain of steps, instead of with a creation wizard?** A wizard would be a fifth form flow beside the four that already exist (create tournament, create edition, create stage, create group) and would hide the domain behind a modal that only makes sense once. The chain is four short pages that each own data of their own — an edition has dates, a stage has a format, a group is where registrations land — so the product teaches it where the work happens: the guide card explains torneo → edición → etapas → partidos before there is data (dashboard and empty tournament list), the first create lands on the tournament's own page, `AdminFlowSteps` marks the step in the chain on each page of it, the step's card opens the next one ("Etapas →") and every empty state names its step. The wizard stays refused until a step needs input from the previous one to be filled in at all.

**Why do form rows that carry a submit button hold no `hint`, and the example lives in the placeholder?** `Field` renders label, control, then `hint`/`error` below, so two fields in a row only line up when their heights match — a hint under one of them pushes the row's `items-end` baseline down and the neighbouring label starts lower than its sibling's. The row that carries the action is therefore the row that keeps examples in the `placeholder` ("2026", "Fase 1", "Grupo A", "Copa Apertura"), the pattern the other admin forms already used. The `hint` stays for a field alone in its row, where it costs nothing; an `error` still moves the button for as long as it is shown, because the message has to be readable.

**Why does `lucide-react` enter through one barrel in `packages/ui` instead of being imported where it is used?** Because the absence of a door is invisible. `apps/web` does not declare the dependency and the layering matrix allows external imports in the web region, so a direct `import { Trophy } from "lucide-react"` in a route compiles, passes every scan and reaches for a package the workspace never declared — a failure with no symptom until the install graph changes under it. `packages/ui/src/components/ui/icon.ts` re-exports the set the product uses (named, one line per icon added when a view asks for it) and nothing outside that module imports the library. Rejected: `export * from "lucide-react"` (lucide exports `Table` and `Sheet` and `@sports/ui` already exports both — the ambiguity breaks the barrel); a name-keyed `<Icon name="trophy" />` map (kills tree-shaking and turns a missing icon into a runtime `undefined`); icon fonts (a third file to load, no per-icon tree-shaking, and the glyphs are prose to the screen reader). The vocabulary lives in that module's header — one term of `CONTEXT.md`, one icon — so the same word wears the same shape in the sidebar, the card and the empty state.

**Why is every icon decorative (`aria-hidden`) instead of carrying a `<title>`?** Because it is a second reading of a word that is already there, and noise for the screen reader. The control carries the accessible name (its text, or its `aria-label` when it is icon-only), so the icon never speaks. This is not taste but the gate: the preset's `lint/a11y/noSvgWithoutTitle` is an error, and an `<svg>` with neither `aria-hidden` nor a `<title>` drops a green run — the rule is what made `DECORATIVE` a shared constant instead of a convention.

**Why do icons accompany the word, and when do they go alone?** A word plus its icon survives a screenshot with the images blocked, a zoom to 200 % and a language the reader does not have; the icon alone survives none of them, so it is allowed only where the action is unmistakable in place — the row's Editar/Eliminar (an aria-label keeps the name), the pager's arrows, the dialog's close. The list is deliberately short: a new icon-only control is a decision, not a default.

**Why do `<option>` labels keep a text arrow (`A → Z`) and the sport glyphs stay emoji?** A `<select>` option holds text, not elements: no icon can go inside it, so the pager's sort labels are the one place the character is honest. The sport and event glyphs (`SportIcon`, `MatchTimeline`) are the same kind of case from the other side — a yellow card is yellow, and no icon font knows what a card is; that is content defined per sport, not the interface's chrome, so it stays as it is and `glyphs` (ADR 007) exempts the line that names it.



**Why is a sport's variant another row of `sports` instead of a `parentId` column?** Because a variant is a regulation, and the regulation is already the row: periods, draws and table points are what differ between fútbol 11, fútbol sala and fútbol 7, or between basketball 5×5 and 3×3 (futsal: two halves, draws, 3/1/0; 3×3: one period, no draws, 2/1). A parent column would group the picker and filter by family, at the price of a contract field plus a migration for something the name already carries ("Fútbol sala"). Reconsider it when the sport picker needs to group or filter by family, not before.

**Why is the sports catalog code in `packages/db` instead of a `.sql` file or data inline in the script?** A typed constant can be tested without a database (ids fit the 32-char column, codes fit 40 and are unique per sport, every sport has at least one scoring event), and the CLI stays a thin printer. The same module is what a future "load catalog" action or a fixture would import; the cost is one package export and an explicit re-run when the catalog changes — seeding is a command, never a boot hook.

**Why does the seed never delete and keep `--force` opt-in?** The dev database is often the only world with hand-made tournaments, and a seed that cleans up before inserting would take them with it. It inserts what is missing; without `--force` it leaves an edited sport or event alone; with `--force` it rewrites only the rows the catalog names. A sport outside the catalog is never touched.

**Why does a scoring event take its value from the event type instead of the payload?** `defaultValue` is the sport's regulation — a triple is 3, a free throw 1 — and the client should not repeat it on every request. The input schema used to default `eventValue` to 1, which made the service's `?? eventType.defaultValue` dead code and every seeded scoring event worth 1. Now an omitted value means the catalog's, and an explicit `eventValue` still overrides it for corrections.

**Why is there no "error that gives the opponent a point" event in the catalog?** A `matchEvent` adds to the team it is recorded for, so an error event would credit the side that committed it. The operator records `point` (or `run`) for the side that won it; point-by-point attribution of the opponent's error would need an `affectsOpponent` flag on the event type — a column, a contract field and a reader in the score recalculation, which no page asks for yet.

**Why does the advance between stages recompute instead of running as a command the organizer triggers once?** A one-shot command hides who qualifies today behind a button nobody remembers to press, and a corrected result after the bracket started leaves the group and the bracket with two truths that drift silently. The advance is a read (`GET /stages/:id/qualifiers`) plus a sync inside the same write that finishes a match, exactly like the standings recalculation (`docs/decided.md`, "Why is the standing of a group recalculated on every score write…"). The only thing that stays explicit is creating the bracket's tree, because that creates rows and creating rows is not a recomputation. Reconsider a one-shot command only if the recomputation cost grows past the group's size (it is bounded by it today).

**Why does automatic group creation only distribute the teams without a group instead of reshuffling the whole stage?** A second click that reshuffles everything is indistinguishable from a click that repairs a half-filled board, and the organizer's manual arrangement is the more expensive state to rebuild. The endpoint therefore creates groups only when there are none (A, B, C…, with `numGroups` required) and otherwise just fills the teams whose `groupId` is still null, balanced by current size. Reconsider a "reorganizar todo" action when the UI can show the difference and ask for it explicitly.

**Why is the target stage's roster derived instead of mixing manual registrations with the qualified?** A target fed by a source with rules has, by definition, exactly the qualified as its entrants. Mixing would need a `source` column per registration (a migration, and `docs/todo.md` P2's empty ledger) to know what to delete when a result changes. v1 assumes manual registration in a derived stage is an anti-pattern; if someone needs extras, they set the rule or register them in a stage without a source. Reconsider the column when a real case of "invited team in a knockout fed by groups" appears.

**Why are byes resolved as finished matches in the bracket instead of being skipped?** A bracket with 6 entrants and 8 slots has 2 byes; skipping them would leave round 1 with 2 matches and round 2 with gaps that the UI and the propagation code would have to special-case. Creating them as finished matches (winner set, status `finished`) keeps every round full and lets the propagation fill the next slot the same way it does for a played match. The cost is 2 extra rows per such bracket, which is the honest count of what the bracket contains.

**Why does a corrected result that already propagated to a started next match return 409 instead of overwriting?** Overwriting would silently move a team in a bracket that already has results, producing an inconsistent llave. The score is saved (the endpoint returns 409 after persisting it) and the organizer fixes the bracket by hand or regenerates it with `force` (only allowed while nothing has started). Reconsider automatic re-propagation when a cascade of corrections becomes a real workflow.
